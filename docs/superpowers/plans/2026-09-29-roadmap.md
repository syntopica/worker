# worker - phased roadmap

Spec: `docs/superpowers/specs/2026-09-29-worker-design.md`. Each phase gets
its own detailed plan before it starts; only phase 1a is detailed now,
because later plans depend on what phase 1a measures.

## Phase 1 - one machine, one model, one arbiter

Split into three plans because it spans three repositories:

| Plan | Repository | Content | Depends on |
| --- | --- | --- | --- |
| 1a | `worker` | Engine: config, store, contract v1, scheduler, API, node with host state and Ollama executor, CLI, Python client, contract fixtures, LaunchAgents. Atrium's local drip lane moves to the queue (task 1a-16). | - |
| 1b | `vexa` | Rust client crate against the 1a fixtures; translation job becomes submit/collect with a local submission table and a single applier; enrichment becomes queue `vexa.enrich` (`active_ok`); interactive ask stays direct. | 1a merged, fixtures published |
| 1c | `worker` | Acceptance on the real workstation: cancel-to-quiet latency on Ollama 0.34.4, zero reloads across the three producers, useful work under repeated interruptions, 1000 translated texts, `status` progress. | 1a, 1b |

Phase 1 is done when 1c's acceptance passes. 1b's plan is written in
`~/p/vexa/docs/superpowers/plans/` when 1a lands, from the fixtures in
`contract/fixtures/`.

## Phase 2 - cost ladder

OpenRouter free executor (20 rpm; daily cap read from `GET /api/v1/key`),
usage ledger and `costs`, quota snapshots keyed by account/window with
freshness, paid-budget reservations, quota-wall cooldowns, `task` kind with
authorized profiles, input manifests, isolated workspaces and
`needs_reconciliation`. Atrium's cursor and agy lanes become `task` jobs and
`drip-loop.sh` retires.

## Phase 3 - absorb the loose scripts

brain/clips codex and agy passes with manifests, periodic classification loops
(agents library-loop), transcription. One TODO per retired script in its owner
repo.

## Phase 4 - more machines

Coordinator moves to the always-on server after its stability gate; Tailscale
binding with LocalAPI WhoIs; `server` node with an enforced memory budget
(ONNX, small models); `guest` nodes after reachability, memory confirmation,
owners' agreement, the fast-user-switching idle test and a small-model
benchmark.
